# Invitation Acceptance Route & Organization Membership Flow

## Context

Organization member invitations are generated by creating `organization_invitations` database records containing unique secret tokens. To process these tokens securely without leaking organization information or creating ambiguous role assignments, dashboard-web requires a dedicated invitation acceptance route and processing pipeline.

This pattern documents the full-stack architecture for invitation validation, privacy-preserving email verification guards, Auth.js sign-in handoffs, canonical user ID resolution, idempotent role provisioning, and token destruction upon redemption.

---

## Technical Guidance & Architecture Patterns

### 1. Canonical User ID Resolution via Postgres Query
When handling form actions in SvelteKit server endpoints (`+page.server.ts`), relying exclusively on `locals.auth()` session user properties can be fragile because Auth.js session strategies (JWT vs database session adapters) may format or omit `user.id`.

To ensure exact database primary key compatibility across all authentication providers, resolve `userId` by querying the `users` table directly using the validated session email address:

```typescript
const userResult = await db
  .select({ id: users.id })
  .from(users)
  .where(eq(users.email, session.user.email))
  .limit(1);

if (userResult.length === 0) {
  throw error(401, 'User account not found');
}
const userId = userResult[0].id;
```

### 2. Alias Route Server Redirection (307)
Invitation emails standardly link to `/invitations/[token]`. To centralize processing under `/auth/accept-invite` without duplicating load logic or template code, the alias route performs an immediate HTTP 307 server-side redirect preserving the query token:

```typescript
export const load: PageServerLoad = async ({ params }) => {
  const { token } = params;
  throw redirect(307, `/auth/accept-invite?token=${encodeURIComponent(token)}`);
```

### 3. High-Contrast Privacy & Security Guard (Email Mismatch)
To prevent unauthorized users from discovering organization names, invited emails, or assigned roles by probing invitation tokens, `+page.server.ts` checks the authenticated session email against the invitation target email:

```typescript
if (userEmail !== inviteEmail) {
  // Security guard: Hide org & invitation details on email mismatch
  return { status: 'email_mismatch' };
}
```

When an email mismatch occurs, the server load returns `{ status: 'email_mismatch' }` without including any organization or invitation metadata in the page data payload. The Svelte template displays a clear account-switch alert, completely preventing organization or token metadata enumeration:

```svelte
{#if data.status === 'email_mismatch'}

    <h3>Account Email Mismatch</h3>
    <p>You are logged in as <strong>{data.userEmail}</strong>, but this invitation was sent to a different email address.</p>
    <p>Please sign out and log in with the invited account to accept this invitation.</p>
  </div>
{/if}
```

### 4. Idempotent Role Provisioning & Token Destruction
When redeeming an invitation via `?/accept`, the system handles member creation, role upgrades, workspace defaults, and token cleanup in a single transaction sequence:

1. **Member Provisioning / Upgrade**: `upsertOrganizationMember()` executes `INSERT INTO organization_members ... ON CONFLICT (user_id, organization_id) DO UPDATE SET role = EXCLUDED.role`, upgrading existing members if invited with a higher role.
2. **User Workspace Preference**: `updateUserLastActiveOrg()` sets `user_session_preferences.last_active_organization_id` to the newly joined organization.
3. **Redemption Cleanup**: `deleteInvitationById()` immediately deletes the invitation record from `organization_invitations` upon redemption.
4. **Duplicate Prevention**: `deletePendingInvitationsByEmail()` purges any prior pending invitation tokens for the target email when creating a new invitation.

```typescript
await upsertOrganizationMember(organization.id, userId, invitation.role);
await updateUserLastActiveOrg(userId, organization.id);
await deleteInvitationById(invitation.id);
throw redirect(303, `/${organization.slug}`);
```

### 5. Defensive Left Join on Organization Queries
In `getInvitationByToken()`, queries joining `organizationInvitations` and `organizations` use a `leftJoin` to handle situations where an organization record may have been deleted while an invitation remained pending:

```typescript
export async function getInvitationByToken(token: string) {
  const [result] = await db
    .select({
      invitation: organizationInvitations,
      organization: organizations,
    })
    .from(organizationInvitations)
    .leftJoin(organizations, eq(organizationInvitations.organizationId, organizations.id))
    .where(eq(organizationInvitations.token, token));

  if (!result || !result.organization) {
    return null;
  }

  return {
    invitation: result.invitation,
    organization: result.organization,
  };
}
```

## Code Examples & Null Safety Rules

- **Hidden Form Inputs**: Always supply string fallback bindings on token form inputs to prevent `undefined` stringification in template renders:
  ```svelte
  <input type="hidden" name="token" value={data.token || ''} />
  ```
- **OAuth / Magic Link Handoff**: Pass `redirectTo` / `callbackUrl` options containing URL-encoded tokens (`/auth/accept-invite?token=${encodeURIComponent(token)}`) to ensure seamless redirection post-login.
